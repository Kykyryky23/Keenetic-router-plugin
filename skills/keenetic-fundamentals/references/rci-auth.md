# RCI-авторизация (challenge / response)

Keenetic RCI использует двухшаговую аутентификацию на основе challenge. Схема официально не
задокументирована, но алгоритм ниже **подтверждён полным успешным round-trip'ом** на реальном
роутере (Keenetic Hero 4G+, KeeneticOS 5.0.12, `POST /auth` → `200 OK`) в ходе разработки
MCP-сервера `keenetic` — это не непроверенная гипотеза, а рабочая реализация.

Показательный урок из этой же разработки: на более ранней стадии здесь был перепутан порядок
хешей (сначала SHA256, потом MD5, вместо MD5-потом-SHA256 ниже) — авторизация стабильно падала
с 401, что несколько часов принималось за «неверный пароль»/«блокировка IP», пока не сверили с
этим самым описанием алгоритма. Если авторизация не проходит, а логин/пароль точно верны —
в первую очередь перепроверь порядок хеширования буквально по шагам ниже, не выше.

Ниже — `http://`, не `https://`: именно так подключается реализация в этом проекте
(`transport/rci-http.ts`, по умолчанию порт 80). У роутера может быть отдельно включён HTTPS для
веб-интерфейса (`ip http ssl enable` в конфиге) — это не проверялось для RCI-авторизации в рамках
этого проекта; если нужен именно HTTPS, схему запроса стоит сверить отдельно, вживую.

## Пошагово

1. **Запрос challenge.**
   `GET http://<router>/auth`
   Если сессия не установлена, роутер отвечает `401 Unauthorized` и кладёт в заголовки:
   - `X-NDM-Realm` — realm (обычно связан с моделью/именем устройства);
   - `X-NDM-Challenge` — случайная строка-вызов на эту попытку.
   Заодно приходит сессионная кука — её нужно сохранять и слать в последующих запросах.

2. **Хеш пароля с realm.**
   `md5 = MD5( "<user>:<realm>:<pass>" )`
   То есть логин, realm и пароль, склеенные через двоеточие, прогоняются через MD5
   (hex-представление).

3. **Ответ на challenge.**
   `sha = SHA256( <challenge> + md5 )`
   Конкатенация строки challenge и полученного md5-хеша, затем SHA-256 (hex).

4. **Отправка ответа.**
   `POST http://<router>/auth`
   Тело — JSON с логином и вычисленным ответом, например:
   ```json
   { "login": "<user>", "password": "<sha>" }
   ```
   Успех — `200 OK`. Далее все запросы к `/rci/...` идут с сохранённой сессионной кукой.

5. **Проверка сессии.**
   Повторный `GET /auth` при живой сессии возвращает `200` (challenge не нужен). Если снова
   `401` — сессия истекла, повтори шаги 1–4.

## Псевдокод

```
resp = GET /auth
if resp.status == 200:            # уже авторизованы
    proceed
realm     = resp.headers["X-NDM-Realm"]
challenge = resp.headers["X-NDM-Challenge"]
cookie    = resp.cookies

md5 = MD5(f"{user}:{realm}:{pass}")          # hex
sha = SHA256(f"{challenge}{md5}")            # hex

POST /auth  body={"login": user, "password": sha}  cookies=cookie
# при 200 — авторизованы; держим cookie для /rci/*
```

## Подводные камни

- **KeenDNS.** Через облачные KeenDNS-домены challenge-авторизация часто ломается в сторонних
  библиотеках (иначе устроен путь запроса). Для автоматизации надёжнее локальный IP или прямой
  доступ, чем KeenDNS.
- **IPv6-доступ к GUI.** Доступ к веб-интерфейсу (и, значит, RCI) по IPv6-адресу роутера
  включён начиная с KeeneticOS 4.0. На более старых прошивках используй IPv4.
- **Истечение сессии.** Куки живут ограниченно. Реализуй «переавторизацию при 401»: получил
  `401` на `/rci/*` → заново пройди `/auth`.
- **Realm зависит от устройства.** Не хардкодь realm — всегда бери из заголовка ответа.
- **Учётка с минимальными правами — но с оговоркой.** Для автоматизации заведи на роутере
  отдельного пользователя с необходимым минимумом прав, а не используй основной `admin` — это
  ограничивает ущерб при утечке ключа. Подтверждено на практике: такой пользователь (тег
  `manager` в веб-интерфейсе) успешно авторизуется по RCI и может читать состояние, управлять
  маршрутами/портами/VPN-биндингом. Но **часть write-команд (в частности, смена Wi-Fi
  пароля) может требовать именно основной `admin`** — если получаешь отказ по правам именно на
  Wi-Fi-командах при рабочих остальных, это не баг авторизации, а ограничение конкретно этой
  учётки.
- **Секреты — не в код и не в чат.** Пароль/учётные данные держи в переменных окружения или
  менеджере секретов, не вставляй их в скрипты и не проси пользователя присылать в открытом виде.
- **Повторные неудачные попытки — не ретрай вслепую.** Keenetic блокирует IP на 15 минут после
  5 неудачных попыток входа за 3 минуты (см. "Brute force protection" в документации Keenetic).
  Если сервер/скрипт явно получил отказ по логину/паролю (не сетевую ошибку) — не повторяй
  попытку с теми же credentials в цикле в надежде на другой результат: он не изменится, а вот
  блокировку так спровоцировать легко (см. `auth/rci-auth.ts` в проекте — там это учтено:
  явный отказ роутера запоминается на весь процесс, повтор с теми же данными не уходит в сеть).
