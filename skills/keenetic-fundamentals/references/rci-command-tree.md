# Дерево команд RCI и сопоставление CLI ↔ RCI

## Главный принцип

RCI — это HTTP-обёртка над тем же деревом команд, что и CLI (`ndmc`). Настройки устройства
маппятся на путь RCI. Поэтому, зная CLI-команду, путь RCI получаешь механически:

```
CLI:  show version
RCI:  GET /rci/show/version

CLI:  show interface
RCI:  GET /rci/show/interface

CLI:  show ip route
RCI:  GET /rci/show/ip/route
```

Каждый пробел в CLI-пути становится сегментом URL после `/rci/`.

## Чтение vs изменение

- **Чтение рантайм-состояния (`show ...`):** `GET /rci/show/...` → JSON с текущим состоянием.
  Подтверждено рабочим для интерфейсов, версии, системной информации, таблицы hotspot-хостов,
  таблицы маршрутов, `associations` (Wi-Fi клиенты), `running-config`.
- **Чтение чистой статической конфигурации — другой механизм, подтверждено на практике.** Узлы
  без рантайм-состояния (проброс портов, DHCP-резервации) отдают 404 на `GET /rci/show/...` и
  читаются только через `POST /rci/` с телом `{"show": {"sc": {<то же дерево>}}}` — именно так
  сам веб-интерфейс роутера запрашивает эти разделы. Пример: список правил port forwarding —
  `{"show":{"sc":{"ip":{"static":{}}}}}`, DHCP-резервации — `{"show":{"sc":{"ip":{"dhcp":{"host":{}}}}}}`.
  Если `GET /rci/show/<путь>` даёт 404 для узла, который точно существует в конфиге (виден в
  `running-config`) — пробуй эту batch-форму, прежде чем считать путь неверным.
- **Изменение/действие:** `POST /rci/` — **обязателен слэш на конце**, подтверждено: без него
  роутер отвечает `405`, а не применяет команду. Тело — JSON, структура которого чаще всего
  повторяет иерархию команды, НО для команд с позиционными CLI-аргументами (`ip route ...`,
  `ip static ...`) подтверждённая рабочая форма — массив объектов с именованными полями, а не
  дерево, ключом которого является один из аргументов (см. подробности и точные примеры в
  `../SKILL.md`, раздел 3 — не дублируем здесь, чтобы не разойтись при обновлении).
- **Батч:** несколько команд можно отправить массивом в одном POST — роутер выполнит их
  по порядку и вернёт массив результатов. Проверяй статус каждого элемента.

## Типы ресурсов

В дереве RCI встречаются разные типы узлов (настройки, действия, статистика). Семантика метода
зависит от типа ресурса: одни узлы только читаются, другие принимают изменения, третьи —
это команды-действия (например сохранение конфигурации, перезагрузка). Не предполагай, что
любой узел писабельный — сверяйся с деревом.

## Где брать точное дерево для конкретной прошивки

1. **Command Reference Manual от Keenetic** (по модели и версии) — источник истины по дереву
   команд. Официальные PDF лежат на `docs.help.keenetic.com` (например каталог `.../cli/<ver>/...`).
   В мануале ищи нужную CLI-команду и переводи её в путь RCI по правилу выше.
2. **`show running-config` / стартовый конфиг** — показывает реально используемые на этом
   роутере ключи и их значения. Это лучшая «карта» перед правкой: видно точные имена
   интерфейсов, туннелей, правил.
3. **Интроспекция через сам RCI** — начни с общих `GET /rci/show/...` и спускайся по дереву,
   чтобы увидеть доступные поддеревья и текущие значения.
4. **Список инструментов MCP-сервера** — если работаешь через MCP, его инструменты и есть
   проверенный набор операций; предпочитай их сырым путям.

## Частые узлы

Часть путей ниже — **подтверждена** на реальном роутере (Keenetic Hero 4G+, KeeneticOS 5.0.12) в
ходе разработки MCP-сервера `keenetic`; часть — типовой ориентир, который стоит проверять на
конкретной прошивке/модели. Помечено явно.

- `show version`, `show system` — версия ПО, аптайм, загрузка CPU/памяти. Подтверждено.
- `show interface` — состояние и счётчики интерфейсов (WAN, LAN, Wi-Fi, VPN-туннели). Подтверждено.
  WAN-интерфейс ищи по рантайм-флагу `"global": true` в этом списке — не по человекочитаемому
  имени (`rename`), которое видно в веб-интерфейсе (это не адресуемый путь).
- `show ip route` — таблица маршрутов. Подтверждено. Policy-routing (в этом роутере встречен как
  `ip policy Policy0` в `running-config`) — отдельный узел, не проверялся детально в этой сессии.
- Список клиентов/хостов — `show ip/hotspot`. Подтверждено.
- Wi-Fi клиенты — `show associations`. Подтверждено.
- Настройки DHCP-резерваций — CLI `ip dhcp host <mac> <ip>`, RCI-путь `ip/dhcp/host`, но читается
  **только** через `{"show":{"sc":{"ip":{"dhcp":{"host":{}}}}}}` (см. выше), не через плоский
  `GET /rci/show/ip/dhcp/host` — тот 404-ит. Подтверждено.
- Проброс портов (NAT) — CLI `ip static <tcp|udp> <interface> <port> <address> [<to-port>]`,
  RCI-путь `ip/static`, читается тем же batch-механизмом: `{"show":{"sc":{"ip":{"static":{}}}}}`.
  Подтверждено, включая точные поля записи (`protocol`, `interface`, `port`, `to-address`,
  `to-port`, `comment`) — см. `network.ts` в проекте.
- Действия: сохранение конфигурации (`system configuration save`), перезагрузка (`system reboot`).
  Не проверялись в этой сессии — пути ориентировочные, сверяй перед использованием.
- VPN-туннели в `show interface` определяются по рантайм-полю `"type"`. Значение `"Wireguard"` —
  **подтверждено** (единственный тип VPN, настроенный на роутере разработки). Остальные типы
  (`OpenVPN`, `IKEv2`, `L2TP`, `PPTP`, `VLESS`) — best-effort по названию, не проверены вживую; если
  встретишь роутер с таким туннелем и его `"type"` не совпадает с ожидаемым, ориентируйся на
  реальное значение поля, а не на список выше.

## Проверяемые правила

- Не заучивай пути как факты — версия прошивки может их сдвинуть. Формулируй так: «типичный
  путь такой-то, проверь для своей прошивки».
- Перед любой записью прочитай текущее значение того же узла — чтобы понимать, что меняешь,
  и иметь возможность откатить.
