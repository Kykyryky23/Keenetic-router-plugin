# Безопасность и пошаговые сценарии

Общий каркас любой операции: **read-first → показать пользователю → подтверждение → write →
verify-after**. Ниже — детализация по типовым задачам.

## Реальный инцидент — почему этот каркас не формальность

При разработке MCP-сервера `keenetic` разведка правильного формата RCI-запроса для добавления
маршрута велась перебором нескольких вариантов payload в цикле, без остановки и проверки между
попытками. Один из вариантов (`{"ip":{"route":["10.0.5.0","255.255.255.255","Wireguard2"]}}` —
массив позиционных значений вместо объекта) роутер интерпретировал не как «добавить маршрут», а
как «очистить все маршруты», и в ответе на это было сообщение `"cleared all routes."` — не
`error`, а обычное `message`. Это осталось незамеченным, потому что после вызова сразу пробовали
следующий вариант, не читая состояние. В результате все статические маршруты на боевом роутере
(включая policy-routing на VPN, которым владелец пользовался ежедневно) исчезли; восстанавливать
пришлось вручную по резервной копии.

Из этого — два конкретных, а не абстрактных правила для любой работы с write-командами RCI:
1. **Один write — одна проверка результата, прежде чем пробовать следующий вариант.** Никаких
   циклов "попробовать несколько форматов подряд" без остановки между ними.
2. **Успешный на вид ответ ("message", не "error") не значит, что произошло именно то, что
   ожидалось.** Всегда перечитывай именно то состояние, которое должно было измениться, и
   сверяй, что изменилось ровно оно и ничего больше.

## Общие правила (напоминание)

- Read-only по умолчанию. Изменения — только с явным «да» в чате.
- Защищённые сущности (WAN, VPN-туннели, маршруты/policy-routing, правила удалённого доступа)
  не трогаем без прямого приказа и предупреждения о риске самоблокировки.
- Reboot — только по запросу, с предупреждением о простое.
- После записи — перечитать состояние и убедиться в результате; статус `error` = провал.
- Уточнять `configuration save` отдельно (изменения применяются сразу, но не переживают
  перезагрузку без сохранения).

## Сценарий: список подключённых устройств

1. Прочитай список хостов/клиентов (RCI-чтение либо MCP-инструмент `list_devices`).
2. Покажи: имя, IP, MAC, интерфейс, онлайн/оффлайн.
3. Никаких изменений — это чистое чтение.

## Сценарий: статическая DHCP-резервация (запинить IP)

1. **Read-first:** прочитай текущие резервации и активные аренды.
2. **Проверки перед записью:**
   - целевой IP не занят другим активным MAC;
   - IP не зарезервирован за другим устройством;
   - идентификатор устройства однозначен (не матчить «66» на `Room-66-Cam`).
3. Сформулируй пользователю: «привяжу IP X к устройству Y (MAC Z)» и дождись подтверждения.
4. Выполни write.
5. **Verify-after:** перечитай резервации, убедись, что привязка появилась и статус не `error`.

## Сценарий: статус WAN / VPN / «есть ли интернет»

1. Прочитай состояние интерфейсов и их счётчиков.
2. Для мульти-WAN — покажи статус по каждому провайдеру отдельно (up/down, приоритет).
3. Для VPN-туннелей (Wireguard/VLESS/IKEv2/OpenVPN) — состояние линка и трафик.
4. Только чтение; ничего не переключай без явного запроса.

## Сценарий: маршруты и policy-routing

1. По умолчанию — только `show ip route` и связанные поддеревья, вывод пользователю.
2. Правки маршрутов — повышенный риск: изменение маршрута, через который идёт управление
   роутером, может привести к самоблокировке.
3. Перед любой правкой: прочитай текущий маршрут, объясни эффект, предупреди о риске,
   получи явное подтверждение.
4. После правки — перечитай таблицу и проверь связность (по возможности не в ущерб доступу).

## Сценарий: проброс портов / файрвол

1. Прочитай текущие правила (filter/NAT) и покажи их пользователю.
2. Объясни эффект предлагаемого правила и его место в порядке правил (порядок важен;
   учитывай connection tracking).
3. Отдельно отметь, если правило затрагивает удалённый доступ (SSH/HTTPS/KeenDNS) —
   это защищённая зона.
4. Подтверждение → write → перечитать правила → проверить статус.

## Сценарий: перезагрузка

1. Только по явному запросу пользователя.
2. Предупреди: все сессии разорвутся, роутер будет недоступен ~1–2 минуты.
3. Уточни, нужно ли сначала сохранить конфигурацию.
4. После подтверждения — выполни; не жди «ответа» от команды как признака успеха.

## Сценарий: сохранение конфигурации

1. Изменения в KeeneticOS применяются немедленно, но не переживают перезагрузку без сохранения.
2. Спроси пользователя, сохранять ли (`system configuration save`).
3. Не сохраняй автоматически после каждой мелкой правки, если пользователь об этом не просил —
   иногда он хочет проверить эффект и откатиться перезагрузкой.

## Красные флаги — остановись и переспроси

- Цель операции неоднозначна (несколько устройств/интерфейсов подходят под описание).
- Операция затрагивает интерфейс/маршрут, через который идёт текущее управление.
- Запрос на массовое изменение (много правил/резерваций разом) без явного пообъектного согласия.
- Ответ RCI содержит `error`/`warning` — не выдавай это за успех, разбери причину.
- Формат write-запроса не проверен вживую на этом устройстве и ты собираешься перебрать несколько
  вариантов подряд — остановись после первого, прочитай состояние, и только потом (с новым
  подтверждением) пробуй следующий (см. "Реальный инцидент" выше).

## Разведка формата RCI-запроса на боевом устройстве (если инструмента MCP для задачи нет)

Если приходится подбирать точный RCI-payload для команды, которой нет среди готовых инструментов
MCP-сервера — это те же самые write-вызовы к реальному роутеру, только цель разведочная, а не
конечная. Правила из раздела 0 `SKILL.md` и "Реальный инцидент" выше применяются без исключений:

1. Сначала `show running-config` (или `system configuration save` + экспорт файла из веб-интерфейса)
   — бэкап текущего состояния, сохранённый **вне** любого репозитория, который может попасть в
   публичный доступ (в конфиге — пароли и ключи в открытом виде).
2. Один вариант payload — одно явное подтверждение пользователя — один вызов.
3. Сразу после — перечитай именно тот раздел состояния, который должен был измениться, и explicitly
   сверь, что больше ничего не поменялось (а не только что "что-то похожее на успех" появилось).
4. Если что-то, кроме цели, изменилось или пропало — немедленно восстанови из бэкапа и останови
   дальнейший перебор, сообщи пользователю, что произошло, прежде чем продолжать.
