# Keenetic Fundamentals

Базовый скилл с доменными знаниями по роутерам Keenetic — часть плагина `keenetic-router-plugin`
(MCP-сервер `keenetic` + этот скилл). Цель — не заменить документацию, а дать модели правильную
**модель работы**: как устроен RCI, как авторизоваться, как узнавать команды вместо угадывания и
как не сломать боевой роутер.

Часть фактов ниже — **подтверждена вживую** на реальном устройстве (Keenetic Hero 4G+,
KeeneticOS 5.0.12) в ходе разработки этого самого плагина, с пометкой "подтверждено". Часть —
типовые ориентиры, которые могут отличаться на другой модели/прошивке, с пометкой "проверяй".
Не путай эти две категории.

## 0. Незыблемое правило — подтверждение перед любой записью на боевой роутер

**Ни один write/destructive-вызов к реальному роутеру — ни через зарегистрированный инструмент,
ни через сырой RCI-запрос, ни как «безобидная проверка формата запроса» — не выполняется без
явного подтверждения пользователя непосредственно перед этим конкретным вызовом.** `dryRun`
не заменяет это правило, если вызов всё же реально отправляется.

Это не абстрактная предосторожность. При разработке этого самого плагина неконтролируемый перебор
вариантов payload в цикле — без проверки результата между попытками — **стёр все статические
маршруты** на боевом, реально используемом роутере, включая policy-routing на VPN, которым
пользователь пользовался ежедневно. Причина: один из проверяемых вариантов формата 
(`{"ip":{"route":["10.0.5.0","255.255.255.255","Wireguard2"]}}`)
на самом деле означал «очистить все маршруты», а не «добавить один» — и это не было замечено,
потому что после вызова не проверили состояние, а сразу пробовали следующий вариант.

Практический вывод: проверяй один write за раз, читай состояние после каждого, и если изменилось
что-то за пределами цели — немедленно восстанавливай из бэкапа и останавливайся, не продолжая
перебор. Перед любой сессией разведки формата RCI на боевом устройстве — сначала вызови
`export_config` (read-only инструмент, полный running-config текстом), сохрани бэкап **вне**
любого публикуемого репозитория (в нём пароли/ключи в открытом виде) и не пересказывай секреты
из него без необходимости.

## 1. Модель работы: RCI и MCP-сервер `keenetic` поверх него

Keenetic управляется через **RCI (Remote Command Interface)** — JSON поверх HTTP, дерево команд,
идентичное CLI (`ndmc`). Многие команды CLI имеют прямое зеркало в RCI: CLI `show version` ↔
HTTP `GET /rci/show/version`. Но не все — см. раздел 3 про "sc"-batch, это подтверждённое
исключение из правила «просто переведи CLI в путь», а не гипотеза.

**Если подключён MCP-сервер `keenetic` — работай через его инструменты**, а не через сырой RCI.
Инструменты разделены на три уровня:

**Read — вызывай свободно, подтверждение не нужно:** `get_version`, `get_system_info`,
`get_interfaces`, `list_devices`, `get_wan_status`, `list_wifi_clients`, `list_port_forwards`,
`list_routes`, `list_dhcp_reservations`, `list_vpn_interfaces`, `export_config`.

**Особый случай — `export_config`.** Формально read-only (ничего не меняет на роутере), но
результат содержит секреты в открытом/слабо обфусцированном виде — хэши паролей пользователей,
WPA-PSK Wi-Fi, параметры WireGuard. Перед вызовом предупреди пользователя, что в ответе будут эти
данные. После получения — не пересказывай и не цитируй секретные значения без необходимости; если
цель — сохранить бэкап, предложи записать его в файл вне git-репозитория, а не оставлять текст
только в переписке.

Перед любым изменением, где нужен id интерфейса (Wi-Fi точка доступа, WAN, VPN-туннель), сначала
вызови `get_interfaces` — id вроде `WifiMaster0/AccessPoint0` у каждого роутера свои, не угадывай.

**Write — обязателен `confirm: true`, желателен `dryRun: true` перед этим:** `set_wifi_password`,
`set_wifi_enabled`, `add_port_forward`, `remove_port_forward`, `add_route`, `remove_route`,
`bind_route_to_vpn`, `unbind_route_from_vpn`, `run_route_batch`, `add_domain_route`. Без
`confirm: true` вызов ничего не применит — это ожидаемо, не повод считать, что сервер сломан.
Перед нетривиальным изменением сначала вызови с `dryRun: true` и покажи пользователю, что именно
будет отправлено, прежде чем вызывать с `confirm: true`. Известное ограничение:
`set_wifi_password`/`set_wifi_enabled` на части роутеров Keenetic требуют именно учётную запись
`admin` — если под текущими кредами получаешь ошибку доступа именно на Wi-Fi-инструментах
(а остальное работает), сообщи об этом пользователю прямо, не пытайся обойти молча.

**`add_domain_route`** — маршрутизация по доменным именам (`object-group fqdn` + `dns-proxy route`)
вместо статических IP-маршрутов; полезно, когда сервис раздаёт трафик с большого/динамического
пула IP, где статический IP-список пришлось бы регулярно обновлять руками. JSON-форма **подтверждена
вживую** — первая попытка по аналогии с `ip route` (голые строки в `include`, `dns-proxy.route`
как массив с ключом `object-group`) провалилась на реальном роутере с ошибкой `"no input"` для
каждого домена; реальная форма (`include` — массив `{address: "..."}`, `dns-proxy.route` — не
массив, а один объект с полем `group`, не `object-group`) была снята перехватом `XHR` на
собственном веб-интерфейсе роутера. Это конкретный пример правила из раздела 4 — не полагайся на
интуитивно логичную форму по аналогии с уже подтверждённой командой другого семейства.

**Destructive — почти всегда откажет, это нормально:** `reboot_router` дополнительно закрыт
флагом `ALLOW_DESTRUCTIVE` в конфигурации сервера (по умолчанию выключен). Если получил отказ
из-за этого флага — не ищи обходной путь, объясни пользователю, что нужно осознанно включить
`ALLOW_DESTRUCTIVE=true` в `.env`, если он действительно этого хочет.

**`run_route_batch`** принимает путь к `.bat`-файлу, но это не настоящий батник — сервер разбирает
его собственной ограниченной грамматикой (`ROUTE ADD/DELETE`, `VPN BIND/UNBIND`), см.
`examples/route-batch.example.bat` в проекте. Не пытайся вписать туда что-то за пределами этой
грамматики — файл целиком отклонится ещё до применения.

Если нужного инструмента нет — скажи об этом пользователю и предложи сырой RCI как явно осознанный
шаг, не притворяйся, что инструмент существует. Если read-вызов возвращает неожиданную структуру
или ошибку — вероятно, для конкретной модели/прошивки путь отличается; не изобретай альтернативный
путь на ходу без подтверждения, сообщи пользователю, что нужна ручная сверка (`npm run smoke` в
проекте сервера).

Сырой RCI напрямую — только когда сервер недоступен или пользователь явно просит. Тогда см.
`references/rci-auth.md` (авторизация) и `references/rci-command-tree.md` (дерево команд/чтение).

## 2. Золотые правила безопасности

1. **Бэкап в начале сессии.** Если в рамках сессии ожидаются изменения на роутере (не только
   чтение) — в самом начале, до первого write-вызова, попробуй получить `export_config` (или
   сырой `show("running-config")`, если MCP-сервер недоступен) как точку восстановления. Если
   бэкап получить не удалось (инструмент недоступен, вызов упал с ошибкой) — **обязательно и явно
   предупреди пользователя об этом до того, как продолжать** с любыми write-вызовами, не
   продолжай молча как ни в чём не бывало.
2. **Read-first.** Сначала прочитай текущее состояние и покажи его пользователю. Только потом
   предлагай изменения.
3. **Изменения — только с подтверждением** (см. раздел 0 — это не совет, а жёсткое правило).
4. **Финальная проверка перед выполнением.** Прежде чем реально отправить write-вызов (уже после
   `dryRun`, уже получив `confirm` от пользователя) — сверь ещё раз про себя: соответствует ли то,
   что будет отправлено, тому, что действительно просил пользователь (правильная цель/id/значение,
   а не то, что осталось от более раннего шага разговора); не выглядит ли payload похожим на
   действие с более широким эффектом, чем предполагается (см. раздел 0 — именно так стёрли все
   маршруты). Это отдельный шаг от получения `confirm`: тот подтверждает намерение пользователя,
   этот — что вызов технически соответствует намерению.
5. **Защищённые сущности не трогай без явного приказа**: WAN-интерфейсы, VPN-туннели,
   policy-routing/таблицы маршрутов, правила файрвола для удалённого доступа (SSH/HTTPS/KeenDNS).
   Ошибка здесь может отрезать пользователя от сети и от самого роутера.
6. **Никаких «слепых» reboot.** Перезагрузка рвёт все сессии.
7. **Сохранение конфигурации.** Изменения в KeeneticOS применяются сразу, но не переживают
   перезагрузку без `system configuration save`. Уточни у пользователя, нужно ли сохранять.
8. **Не подставляй недостающие данные.** Идентификаторы «по номеру» не должны нечётко матчиться
   на имена. Если цель неоднозначна — переспроси.
9. **Читай ответ RCI обратно.** После write-вызова перечитай состояние (`list_*`/`get_*`) и
   убедись, что оно изменилось как ожидалось. Статус `error`/успешное на вид сообщение без
   реального изменения в перечитанном состоянии — это провал, а не «наверное сработало» (см.
   раздел 0 — именно так пропустили стирание маршрутов: ответ выглядел как обычное сообщение,
   а не как явная ошибка).

Подробные пошаговые сценарии — в `references/safety-and-workflows.md`.

## 3. Топология RCI — подтверждённые нюансы транспорта

- Базовый эндпоинт для записи: `POST /rci/` — **обязателен слэш на конце**, без него сервер
  отвечает 405 (подтверждено). Чтение простых/рантайм-узлов: `GET /rci/show/<путь>`.
- **Не все узлы читаются через `GET /rci/show/...`.** Узлы чистой статической конфигурации без
  рантайм-состояния (проброс портов, DHCP-резервации) отдают 404 на `GET show` и требуют вместо
  этого batch-запрос **тем же `POST /rci/`**: тело вида `{"show":{"sc":{...}}}`, где путь после
  `sc` — то же дерево, что и у обычной команды (например `{"show":{"sc":{"ip":{"static":{}}}}}`
  для правил port forwarding, `{"show":{"sc":{"ip":{"dhcp":{"host":{}}}}}}` для DHCP-резерваций).
  Это подтверждено — тем же способом, которым сам веб-интерфейс роутера читает эти разделы.
- **Запись — массив объектов, а не дерево по ключу.** Для команд вида `ip route`/`ip static`
  (CLI `<command> <позиционные-аргументы>`) правильная JSON-форма — массив объектов с именованными
  полями под родительским ключом (`{"ip":{"route":[{"network":..., "mask":..., "interface":...}]}}`),
  **не** вложенное дерево `{"ip":{"route":{"<сеть>":{...}}}}}`, которое интуитивно ожидалось бы по
  прямому CLI-маппингу. Оба варианта принимаются без явной ошибки на вход, но только массив реально
  применяет изменение — на это стоит обратить внимание при отладке новых команд.
- **Удаление — поле `no: true` внутри элемента массива**, а не внешняя обёртка `{"no": {...}}}`.
  Обёртка возвращает `"not found: no/ip/route"`. Подтверждено на удалении маршрута; для остальных
  подобных команд (например `remove_port_forward`) форма реализована по аналогии, но **не
  проверена вживую** — перепроверь с `dryRun`/явным подтверждением перед боевым использованием.
- **`metric` у `ip route` НЕ даёт приоритет между двумя `auto`-маршрутами на одну цель, когда оба
  интерфейса подняты одновременно — проверено вживую, и результат обратный ожиданиям.** Два
  маршрута на один адрес (основной интерфейс с `metric: 1000`, второй — заведомо худший
  `metric: 2000`) — активным в реальной таблице стал именно худший по metric. То же самое
  повторилось независимо на боевых маршрутах без всякого metric вообще, когда второй интерфейс
  просто подняли — реальный трафик молча перескочил на него. Судя по обоим случаям, критерий выбора
  — «какой интерфейс поднялся позже», а не `metric`. **Не держи два `auto`-маршрута на одну цель с
  одновременно поднятыми интерфейсами в бою** — непредсказуемо, какой окажется активным. Безопасный
  резерв на сегодня — второй маршрут с интерфейсом, административно выключенным до ручного
  переключения (не автоматический failover). Если нужно re-проверить — только на тестовом адресе
  (например `203.0.113.0/24`, TEST-NET-3, зарезервирован документацией, не задействует реальный
  трафик), не на боевых записях.
- **`show sc` может на 1-2 секунды отставать от только что сделанной записи** (кэш на стороне
  роутера) — если сразу после write повторное чтение "не видит" изменение, не спеши считать
  payload неверным: перепроверь через `show("running-config")`, который отражает изменения
  мгновенно, или подожди секунду и перечитай снова.
- **WAN-интерфейс адресуется по базовому id, не по пользовательскому rename.** В веб-интерфейсе он
  может называться "ISP" или как угодно ещё — RCI знает его только по исходному id вида
  `GigabitEthernet1`, который к тому же отличается между моделями роутеров. Не хардкодь имя —
  бери id из `get_interfaces`/`show("interface")`, отфильтровав по рантайм-флагу `"global": true`.
- **Wi-Fi WPA-PSK** — значение обязано быть вложено в объект: `{"authentication":{"wpa-psk":{"psk":
  "..."}}}`. Плоская строка вместо `psk` даёт ошибку `"no input"`; форма с массивом сначала **удаляет**
  существующий пароль, а потом падает с той же ошибкой — не пробуй её.
- **Часть настроек (в т.ч. смена Wi-Fi пароля) может требовать именно основной аккаунт `admin`**,
  а не второстепенного пользователя с урезанными правами.

Полное дерево команд и как узнавать пути для узлов, которых нет в списке выше — в
`references/rci-command-tree.md`.

## 4. Узнавай команды, а не угадывай — но проверяй, а не гадай "интуитивно правильную" форму

RCI слабо документирован официально, поэтому: (1) дерево CLI = дерево RCI по структуре путей —
если знаешь CLI-команду, путь получаешь механически; (2) `show running-config` — лучшая карта
реальных ключей конкретного роутера; (3) если формат write-команды неочевиден (как в разделе 3
выше) — не полагайся на "логичный" вариант с первой попытки, проверяй с подтверждением
пользователя и читай состояние после. См. `references/rci-command-tree.md` для деталей и
источников (Command Reference Manual по моделям).

## 5. Типовые сценарии

**Посмотреть подключённые устройства** — `list_devices`, чистое чтение.

**DHCP-резервация (запинить IP)** — read-first (`list_dhcp_reservations`, проверить, что IP не
занят другим MAC), затем write с подтверждением, затем verify-after.

**Статус WAN/VPN** — `get_wan_status`/`list_vpn_interfaces`, чтение состояния и счётчиков; ничего
не переключай без явного запроса.

**Маршруты и policy-routing** — по умолчанию только чтение (`list_routes`). Правки — повышенный
риск (см. раздел 0 — именно тут произошёл реальный инцидент), только с подтверждением и явным
предупреждением о риске самоблокировки/потери маршрутизации критичного трафика.

**Проброс портов** — `list_port_forwards` сначала, объясни эффект предлагаемого правила
(`add_port_forward`), дождись подтверждения, `dryRun` для предпросмотра.

**Перезагрузка** — только по явному запросу, с предупреждением о простое; уточни необходимость
сохранения конфигурации; помни, что `reboot_router` в принципе заблокирован без `ALLOW_DESTRUCTIVE`.

Развёрнутые пошаговые чек-листы — в `references/safety-and-workflows.md`.

исправить, или явно недоволен результатом — это сигнал не только исправить конкретный ответ, но
и проверить сам скилл. **Всегда анализируй, в чём была неточность или пробел в `SKILL.md`/
`references/*.md`, и явно предлагай пользователю конкретную правку** — что именно добавить или
изменить и где — а не только чини ответ в моменте и не жди, что пользователь сам скажет "обнови
файл". Разовое исправление без обновления скилла означает, что та же ошибка или та же неточность
повторится в следующей сессии — ровно то, от чего предостерегает правило про обязательную
актуальность `CLAUDE.md` в корне проекта; для скилла оно действует так же.

## Как расширять этот скилл

Узкие темы — отдельными скилл-папками (`keenetic-firewall`, `keenetic-vpn` и т.д.), каждая со
своим `SKILL.md`, со ссылкой на этот базовый. Новые подтверждённые вживую факты о формате RCI —
сразу в раздел 3 этого файла с пометкой "подтверждено", а не в отдельный забытый файл.
